# استراتيجية الاختبارات

## الطبقات

1. **مرجعية:** حالات مأخوذة من الديسكتوب لتثبيت النتائج المقبولة.
2. **وحدة:** قواعد الأسعار والأوزان والتصنيع والتقريب وحالات المستندات.
3. **تكامل:** PostgreSQL حقيقية، معاملات، قيود، أقفال وFIFO.
4. **عقود API:** شكل الطلب والاستجابة والأخطاء والصلاحيات.
5. **واجهة كاملة:** رحلات المستخدم الحرجة من المتصفح.
6. **تزامن:** خمسة مستخدمين ينفذون صرفًا وترقيمًا وتسليمًا في الوقت نفسه.
7. **أداء وأمان:** قبل الإطلاق وعلى صورة الإنتاج نفسها.

## بوابة الدمج

لا يمر أي تغيير إذا فشلت اختبارات المجال، أو migration، أو الصلاحيات، أو البناء، أو ظهرت ثغرة حرجة في تبعية مباشرة.

## السيناريوهات الذهبية الأولى

- تخطيط خلطة متعددة المخرجات مع خردة معاد استخدامها.
- إكمال تصنيع مع خامات غير مستخدمة وانحراف وزن.
- تخصيص FIFO مع طبقات متعددة وتزامن عمليتي صرف.
- كارتة وزن إجمالية موزعة على عدة منتجات مع فروق التقريب.
- بيع بالوزن ثم مرتجع يعيد الوزن والكمية والتكلفة إلى الطبقات الصحيحة.

## سيناريوهات الهوية المعتمدة

- تدوير رمز التجديد وإبطال الجلسة عند تسجيل الخروج.
- رفض الطلب المعدّل عند غياب CSRF حتى مع وجود جلسة صالحة.
- رفض استدعاء API مباشر من مستخدم لا يملك الصلاحية وتسجيل الواقعة.
- منع الحساب ذي كلمة المرور المؤقتة من تجاوز شاشة التغيير عبر API.
- إبطال جلسات المستخدم فور تعطيله أو تغيير أدواره.
- قفل الحساب بعد عدد المحاولات الفاشلة دون كشف ما إذا كان اسم المستخدم موجودًا.

## سيناريوهات البيانات الأساسية المعتمدة

- رفض الأكواد المكررة بعد التطبيع حتى مع اختلاف حالة الأحرف.
- رفض تحديث قديم باستخدام رقم النسخة بدل الكتابة فوق تعديل مستخدم آخر.
- منع الدورات في شجرة تصنيفات المنتجات.
- ضمان وجود مخزن افتراضي واحد ومنع تعطيله قبل تعيين بديل.
- رفض جميع عمليات الكتابة لمستخدم يملك صلاحية العرض فقط.
- تخصيص خمسة أرقام مستندات متزامنة على PostgreSQL دون تكرار.

## سيناريوهات المخزون الجاري اعتمادها

- FIFO يستهلك أقدم طبقة أولًا ويحفظ تكلفة كل تخصيص بدل المتوسط المتحرك.
- تتبع الكمية والوزن المزدوج مع توزيع البعد المقابل تناسبيًا داخل الطبقة.
- إعادة طلب الاستلام أو الصرف بمفتاح منع التكرار نفسه لا تنشئ حركة ثانية.
- رفض الصرف الأكبر من الرصيد دون حركة أو تخصيص جزئي.
- خمس عمليات صرف متزامنة تنتظر أقفال PostgreSQL ولا تتجاوز الرصيد.

## سيناريوهات المبيعات الجاري اعتمادها

- بيع القطعة يخصم العدد والوزن المقابل وتكلفة FIFO وينشئ فاتورة عميل مرة واحدة.
- كارتة الوزن تخصم العدد والوزن التجاري الفعلي مع تطابق مجموع البنود مع وزن الكارتة.
- إعادة مفتاح منع التكرار لا تنشئ تسليمًا أو فاتورة أو حركة مخزون ثانية.
- عكس التسليم يعكس الفاتورة ويعيد الكمية والوزن والتكلفة إلى طبقات FIFO الصحيحة.
- صلاحيات مبيعات القطعة والوزن معزولة عند العرض والإنشاء والتسليم والعكس.
- خمسة طلبات متزامنة لتسليم الأمر نفسه تنجح مرة واحدة فقط على PostgreSQL.
- عرض السعر لا ينشئ أمر بيع أو فاتورة أو حركة مخزون.

## سيناريوهات الخزينة الجاري اعتمادها

- توزيع تحصيل واحد على أكثر من فاتورة مع رفض أي مبلغ يتجاوز المتبقي.
- حفظ الجزء غير الموزع كدفعة مقدمة ثم ربط دفعة الأمر تلقائيًا عند ترحيل الفاتورة.
- إنشاء أمر بيع أو شراء ودفعة مقدمة في معاملة واحدة، والتراجع الكامل عند فشل أي طرف.
- توافق طريقة الدفع مع نوع الحساب المالي، مع بقاء سداد المورد السالب مطابقًا للديسكتوب.
- التحويل والتسوية والعكس بمفتاح منع تكرار ودون رصيد أو سجل جزئي.
- الرصيد الافتتاحي وتسوية العميل والعكس وكشف الحساب يعيدون الرصيد نفسه حسابيًا.
- خمسة تحصيلات متزامنة لا تخصص الفاتورة نفسها أكثر من مرة على PostgreSQL.
- مستخدم `accounts.read` يرى الشاشة دون أدوات الكتابة، ومن لا يملكها لا يرى الوحدة
  ولا يستطيع استدعاء API مباشرة.
