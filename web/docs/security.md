# خط أساس الأمان

## الهوية

- لا يوجد تسجيل عام للمستخدمين.
- إنشاء المستخدمين وتغيير أدوارهم لصاحب صلاحية الإدارة فقط.
- كلمات المرور تُخزّن باستخدام Argon2id.
- جلسات قصيرة داخل Cookies من نوع `HttpOnly`, `Secure`, `SameSite`.
- تدوير جلسة التجديد وإبطالها عند تسجيل الخروج أو تعطيل المستخدم.
- تحديد محاولات تسجيل الدخول دون كشف وجود اسم المستخدم.
- رمز الوصول قصير العمر، وكل طلب يتحقق أيضًا من الحساب والجلسة لضمان الإبطال الفوري.
- رمز التجديد لا يُخزّن بصورته الأصلية، وحماية CSRF تستخدم Cookie مع Header مطابق.
- كلمة المرور المؤقتة تمنع الوصول إلى الوحدات حتى يغيّرها المستخدم.
- إنشاء المدير الأول بأمر تفاعلي مرة واحدة؛ لا تُمرر كلمة المرور في سطر الأوامر.

## التفويض

- نموذج `user -> roles -> permissions` مع إمكانية أكثر من دور للمستخدم.
- فحص الصلاحية في طبقة API والخدمة، وليس الواجهة فقط.
- صلاحيات منفصلة للعرض والإنشاء والتعديل والاعتماد والإلغاء وعرض التكلفة.

## البيانات والتشغيل

- أسرار الإنتاج خارج Git وصور Docker.
- PostgreSQL لا يُنشر على الإنترنت.
- HTTPS إلزامي في الإنتاج.
- رسائل الأخطاء العامة لا تتضمن SQL أو tracebacks.
- سجل تدقيق للمدفوعات والمخزون والتصنيع والصلاحيات.
- نسخ احتياطي مشفر واختبار استعادة دوري.

## بوابات الجودة الأمنية

- فحص تبعيات Python وNode.
- فحص أسرار ومفاتيح بالخطأ داخل Git.
- تحليل ثابت للكود.
- اختبارات صلاحيات سالبة لكل endpoint حساس.
- فحص OWASP ديناميكي قبل الإطلاق.

## ما نُفذ في المرحلة 2

- Cookies من نوع `HttpOnly` لرمزي الوصول والتجديد، و`Secure` في الإنتاج، و`SameSite=Strict`.
- تدوير Refresh Token وCSRF Token عند كل تجديد وإبطال جميع الجلسات عند التعطيل أو تغيير الدور.
- قفل الحساب بعد المحاولات الفاشلة، وحد إضافي لمحاولات المصدر خلال نافذة زمنية.
- سجل تدقيق لنجاح وفشل الدخول، ورفض CSRF والصلاحيات، وتغييرات المستخدمين والأدوار.
- منع تعديل المستخدم لأدواره أو تعطيل حسابه بنفسه، ومنع تعديل الأدوار الأساسية.

## ما نُفذ في المرحلة 3

- فصل صلاحيات العرض والإدارة للمنتجات والشركاء والمخازن والإعدادات، وفرضها داخل API.
- حماية كل عمليات الكتابة برمز CSRF مع تسجيل محاولات رفض الصلاحية.
- تطبيع الأكواد وفرض قيود فريدة في قاعدة البيانات مع تحويل التعارض إلى استجابة آمنة.
- استخدام optimistic concurrency في كل سجلات البيانات الأساسية القابلة للتعديل.
- منع وجود أكثر من مخزن افتراضي بقيد جزئي داخل PostgreSQL.
- تسجيل الإنشاء والتعديل وحالة السجل في سجل التدقيق دون تسريب أخطاء SQL.

## ما نُفذ في المرحلة 6

- فصل صلاحيات عرض وإدارة مبيعات القطعة عن صلاحيات عرض وإدارة البيع بالوزن.
- فلترة قائمة الأوامر والتحقق من نوع الفاتورة داخل API قبل العرض أو التسليم أو العكس.
- حماية كل عمليات الكتابة بـCSRF ومفاتيح منع التكرار للتسليم والعكس.
- قفل أمر البيع وطبقات FIFO داخل معاملة PostgreSQL لمنع البيع المزدوج.
- تسجيل إنشاء الأمر والكارتة والعرض والتسليم والعكس في سجل التدقيق.
