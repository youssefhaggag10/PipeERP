## 1. الخلاصة التنفيذية

PipeERP نظام ERP عربي لإدارة مصنع مواسير بلاستيك. توجد له نسختان في نفس المستودع:

- تطبيق Desktop على فرع `main`، وهو المرجع لقواعد العمل الأصلية.
- تطبيق Web على فرع `web-rebuild`، مبني بـReact وFastAPI وPostgreSQL وDocker.

نسخة الويب تجاوزت مرحلة النموذج الأولي، وتحتوي الآن على الوحدات التشغيلية الأساسية:
الهوية والصلاحيات، لوحة التشغيل، المنتجات والشركاء، CRM، المخزون وFIFO والدفعات،
المشتريات، المبيعات بالقطعة والوزن، الخزينة والحسابات، التصنيع، المرتجعات، التقارير
وطباعة A4، بالإضافة إلى أدوات التشغيل والنسخ الاحتياطي والمراقبة.

المرحلة التقنية من 0 إلى 10 مكتملة. المرحلة 11 - القبول والتقوية والنشر - ما زالت
قيد التنفيذ لأنها تحتاج قبول مستخدم فعلي UAT، وتجربة على أجهزة موبايل حقيقية، وطباعة
فعلية، وبيانات VPS ونطاق ونافذة نشر.

النسخة ليست موصوفة هنا بأنها مطابقة بصريًا للديسكتوب 100%؛ الهدف المعتمد هو مطابقة
قواعد العمل والنتائج المهمة مع واجهة ويب حديثة ومتجاوبة. توجد إضافات ويب معتمدة وفروق
مقصودة موثقة أدناه.

## 4. الهدف والقرارات المعتمدة

### الهدف

- نقل قواعد عمل الديسكتوب إلى تطبيق ويب احترافي ومتجاوب.
- الحفاظ على صحة FIFO والأوزان والتصنيع والتكلفة والحسابات.
- دعم حتى خمسة مستخدمين يكتبون في الوقت نفسه دون صرف أو بيع مزدوج.
- تقديم تطبيق عربي RTL يعمل من الكمبيوتر والموبايل من نفس الرابط.

### قرارات ثابتة

- PostgreSQL 17 هو مصدر الحقيقة الوحيد لنسخة الويب.
- Alembic هو المسار الوحيد لتغيير مخطط قاعدة البيانات.
- `Decimal` في Python و`NUMERIC` في PostgreSQL للأموال والكميات والأوزان.
- لا تستدعي الواجهة قاعدة البيانات مباشرة؛ المسار هو:
  `API -> Service -> Domain Rules -> Repository/ORM -> PostgreSQL`.
- العمليات الحساسة داخل معاملات ذرية وتستخدم أقفال صفوف عند الحاجة.
- مفاتيح منع التكرار Idempotency تمنع تكرار الترحيل بسبب إعادة الطلب.
- الصلاحيات تُفرض في API والخدمات، وليس بإخفاء الأزرار فقط.
- الطباعة المعتمدة للويب A4. الطباعة الحرارية 80mm خارج النطاق الحالي.
- لا توجد تكاملات خارجية في الإصدار الأول.
- لا يعمل الديسكتوب والويب على نفس بيانات الإنتاج بالتوازي بعد التسليم.

### 6.5 المخزون وFIFO

الحالة: **موجود ومختبر مع التزامن والعكس**.

- استلام وصرف وتحويل وتسوية مخزون.
- منع الرصيد السالب والتخصيص المزدوج.
- FIFO بطبقات تكلفة فعلية.
- تتبع الكمية والوزن معًا.
- دفعات/Lots وتكلفتها والمتبقي منها.
- التحويل الذري بين المخازن.
- عكس الحركات مع الحفاظ على السجل التاريخي.
- أرصدة حالية، أرصدة دفعات، وكارت صنف.

#### أرصدة الدفعات

مكانها: **المخزون -> أرصدة الدفعات**. كان اسم التبويب في الويب سابقًا "أرصدة
التشغيلات" وتم تصحيحه إلى الاسم المطلوب.

تعرض الدفعة، تاريخ الاستلام، المستلم، المصروف، المتبقي، متوسط التكلفة والقيمة وفق FIFO.

#### كارت الصنف

مكانه: **المخزون -> كارت الصنف**.

تمت مراجعة منطق الديسكتوب أولًا ثم تعديل الويب في الالتزام `8278d03`. الأعمدة المهمة
الآن هي نفسها في المرجع:

1. التاريخ.
2. الكود.
3. الصنف.
4. المخزن.
5. الدفعة.
6. داخل.
7. خارج.
8. التكلفة.
9. المرجع.
10. الطرف.

الصرف يوسّع تخصيصات FIFO إلى أسطر الدفعات الأصلية بدل عرض حركة مجمعة فقط. لذلك يظهر
رقم الدفعة وتكلفتها الفعلية لكل طبقة. كما تظهر المراجع المفهومة مثل أرقام سندات الشراء
والبيع والمرتجعات وأوامر التصنيع، ويظهر المورد أو العميل المرتبط.

يوجد في الويب فلتر اختياري للصنف مع اختيار افتراضي **كل الأصناف**. هذا تحسين استخدام
إضافي ولا يغيّر منطق الكارت.

- مسودة ثم اعتماد ثم استلام.
- استلام جزئي ثم كامل - إضافة ويب وافق عليها المالك.
- إنشاء Lot تلقائي عند الاستلام.
- تسجيل الفاقد والكميات والأوزان الصافية.
- رسملة التكلفة الداخلية على المخزون المقبول.

- ربط الدفعات المقدمة بالفاتورة.
- عكس فاتورة المورد، ثم السماح بعكس سند الاستلام عندما تكون الشروط آمنة.
- رفض عكس طبقة تم استهلاكها بما يمنع تشويه FIFO.

ملاحظة تاريخية: مشكلة القيد المالي لفاتورة المورد وغياب عكسها كانت ضمن مراجعة قديمة؛
الكود الحالي يحتوي دورة عكس فاتورة المورد واختبارات مرتبطة بها.

### 6.7 المبيعات بالقطعة والوزن

#### إصلاحات الموبايل

- سبب الصفحة البيضاء القديمة كان الاعتماد المباشر على `crypto.randomUUID` الذي قد لا
  يتوفر عند فتح النظام عبر HTTP من عنوان الشبكة على بعض متصفحات الموبايل.
- أضيف مولد `clientId` مع fallback واختبار مخصص، واستُبدلت الاستخدامات الحساسة به.
- الواجهة المحلية أصبحت مربوطة على `0.0.0.0:5173` لتُفتح من أجهزة الشبكة.
- أضيف Error Boundary لمنع اختفاء الواجهة بالكامل عند خطأ غير متوقع.
- مشكلة قص الجزء العلوي في المبيعات عند الدخول من لوحة التشغيل عولجت في `c0827d5`:
  رابط الإنشاء على الموبايل يعيد الصفحة إلى أعلى بدل الاحتفاظ بموضع تمرير غير صحيح.

المبيعات والمشتريات لم تعدا مصممتين لتظهرا كصفحة بيضاء على الموبايل، لكن القبول النهائي
يحتاج تجربة فعلية على iPhone Safari وAndroid Chrome لأن محاكاة المقاس وحدها لا تغطي
كل اختلافات المتصفحات.

- لا توجد طباعة حرارية 80mm؛ الطباعة A4 هي النطاق المعتمد.
- النسخ والاستعادة عمليات خادم، وليست زرًا يسمح لمستخدم المتصفح باستبدال قاعدة الإنتاج.
- كشف حركة الشريك داخل الحسابات بدل تكراره في بطاقة العميل/المورد.

### خصائص Desktop غير منقولة حتى الآن

- بعض إعدادات المظهر الخاصة بالديسكتوب.
- شعار هيدر ثابت بجوار اسم المستخدم؛ تُنقل إليه تلقائيًا صورة العلامة المائية المحفوظة سابقًا.
- تعدد أرقام الهواتف بالشكل الموجود في إعدادات الديسكتوب.

هذه النقاط تحتاج قرار مالك المشروع: هل تُنقل للإصدار الأول أم تُسجل كتحسين لاحق؟

## 10. التشغيل المحلي

### المتطلبات

- Git.
- Docker Engine.

### الإعداد لأول مرة

```bash
cp .env.example .env
```

ضع قيمًا محلية قوية في `.env`، ثم:

### إنشاء أول مدير

```bash
sudo docker compose exec backend python -m app.modules.identity.bootstrap \
  --username admin --display-name "مدير النظام"
```

### فتح النظام من الموبايل على نفس الشبكة

1. اعرف عنوان IP للكمبيوتر على الشبكة.
2. افتح من الموبايل: `http://IP-OF-PC:5173`.
3. يجب أن يكون الجهازان على نفس الشبكة وألا يمنع Firewall المنفذ 5173.
4. الواجهة مربوطة حاليًا على `0.0.0.0:5173` لهذا الغرض.

## 12. الأمان والتدقيق

- كلمات المرور Argon2id ولا تُخزن كنص.
- Cookies من نوع HttpOnly وSameSite، وSecure في الإنتاج.
- CSRF للطلبات الكتابية.
- صلاحيات API منفصلة للعرض والإدارة والوحدات الحساسة.
- PostgreSQL غير منشور للإنترنت في إعداد الإنتاج.
- HTTPS إجباري في الإنتاج.
- الأسرار خارج Git وتُركب كDocker secrets.
- رسائل الخطأ لا تكشف SQL أو tracebacks للمستخدم.
- سجل تدقيق للهوية والمخزون والمدفوعات والتصنيع والصلاحيات.
- لا تُحذف الحركات المعتمدة لتصحيحها؛ يستخدم العكس مع السبب والأثر التاريخي.
